# Configuration Overview

Choose the input by what you are deploying:

- **A private DPN dataspace on existing validators:** use the small
  [dataspace definition](../../dataspaces/dpn.toml). It contains no validator or
  network-service settings. `iroha dataspace plan/apply/status <definition>
  --trust <public-profile.json>` owns planning, submission and recovery. The
  runtime currently requires an HTTPS parent with four authenticated NPoS
  validators; no validator configuration or client TOML is required. See the
  [deployment implementation status](../network_deployment.md).
- **A validator process:** use the [validator example](../../configs/validator.example.toml).
  The sections below describe this process configuration, not dataspace inputs.
- **A whole network:** use the network definitions in `networks/` and the
  [deployment design](../network_deployment.md).

The exhaustive `specs/references/peer.template.toml` is a parameter reference,
not a dataspace setup checklist.

Defaults first: configuration values are curated for typical Iroha blockchain deployments. In most cases, you can run with the defaults unchanged. Only adjust settings when you have a specific operational need (e.g., custom ports, strict rate limits, or known network constraints).

- Sora-specific sections (`sorafs.*`, multi-lane `nexus.*`) require starting the daemon with `iroha3d --sora …` (or exporting `IROHA_SORA_PROFILE=1`). Without the flag the loader rejects configurations that enable those features.
- Nexus routing is mandatory in the first release and has no availability switch; `enabled` is an unknown key in `[nexus]`. The canonical one-lane catalog uses the transaction-aware `ConfigLaneRouter`; multi-lane/Sora topology overrides additionally require the Sora profile and authenticated NPoS consensus mode.
- `[common]`: Chain identity (`chain`), node key pair, trusted peers, and the i105 display discriminant (`chain_discriminant`). `chain` is exact, case-sensitive ASCII of 1–128 bytes; it starts and ends with an alphanumeric and otherwise permits only alphanumerics plus `.`, `_`, `:`, and `-`. Assign a unique value to every distinct deployment/replay domain. `AccountId` and `AccountAddress` are universally scoped and domainless; domain routing uses explicit `DomainId` and account-alias records, never a node-local default label.
- Identity separation: `public_key` plus exactly one of `private_key` or `private_key_file` forms the node's transport + consensus identity and must be BLS‑Normal for validator nodes. Production profiles use `private_key_file`; the file is read once through a bounded descriptor, must contain one canonical key, and on Unix must not grant group/other access. The same exact-one-source rule applies to the dedicated SoraNet transport key (`soranet_transport_private_key` or `_file`). Validator identities must appear in `trusted_peers` alongside a valid PoP in `trusted_peers_pop`. Trusted peers without PoPs are network-trusted observers and are excluded from consensus. Config parsing rejects invalid PoPs or PoP maps that reference keys outside `trusted_peers`. `crypto.allowed_signing`/`allowed_curve_ids` gate transaction admission and non-consensus account controllers; BLS validator accounts are accepted even if `allowed_signing` omits BLS. Add `bls_normal` to `allowed_signing` only when you intend to accept BLS‑signed transactions.
- `data_dir`: Fixed node directory layout. When set, every state path the file does not set explicitly (`kura.store_dir`, `snapshot.store_dir`, `tiered_state.{cold_store_root,da_store_root}`, `streaming.session_store_dir`, `soracloud_runtime.state_dir`, `network.soranet_handshake.pow.revocation_store_path`, `torii.data_dir`, `torii.da_ingest.{replay_cache_store_dir,manifest_store_dir}`, `sorafs.storage.data_dir`, `sorafs.por.state_dir`) defaults under `<data_dir>/state/`, and every secret file defaults to a fixed name under `<data_dir>/secrets/`: `validator.key` (`private_key_file`), `transport.key` (`soranet_transport_private_key_file`), `streaming.key` (`streaming.identity_private_key_file`), `authority/{faucet,onboarding}.key` (when that Torii section is configured), plus `runtime_signer.key`, `beacon.cred` and `authority/sorafs_council.key` for the node-secret loader. An inline key or explicit per-path value wins. A relative `data_dir` resolves against the directory of the file that sets it and is then made absolute against the working directory (lexically, `..` removes the preceding component), so every derived path is absolute. The derived defaults are completed by `iroha_config::node_config`, which writes the resolved `data_dir` to its own source; a configuration read without it that sets `data_dir` is rejected (`Invalid node data directory`). `soranet_transport_public_key` and `streaming.identity_public_key` may be omitted; they are then derived from the private key.
- Compiled profiles: set `profile` (`sora-nexus-v1`, `sora-nexus-v1-qual` or `iroha-dev-v1`), `validators` (the network's validator count, not its seed-peer count), and `data_dir`. Optional `role` is `validator` by default, or `lane_validator` / `observer`. This is the only node-role selector: the loader derives `sumeragi.role` and `chain_discriminant` from the selection. Writing either derived setting in a profile node file is an error. The retired `role_overlay` and `profile_roster_size` selectors are rejected, with no aliases.
  Layers are code defaults, profile `static`, `derive(validators)`, profile `policy`, role, then per-node inputs. Node inputs are restricted to identity/bootstrap bindings, addresses, runtime signer and Inrou bindings, lifecycle and the profile's `node_tunable` logger settings; the exact allowlist is `iroha_config::profile::PROFILE_NODE_KEYS`. Unknown or policy-owned keys produce errors naming the file and key. Profile files cannot use `extends` or `--sora`. The `torii.faucet` and `torii.account_onboarding` policy templates apply only when the node file binds their authorities. Profiles live in `crates/iroha_config/profiles/`; see [deployment design](../network_deployment.md) §3.8 and §10 and [simplification goals](../configuration_simplification.md).
- `[lifecycle]`: `exit_on_stdin_close` (default `false`) makes the daemon exit when standard input reaches end-of-file; only a supervising parent that holds the pipe sets it.
- `[genesis]`: Location of the operator-provisioned signed genesis file, the public key used to verify it, and exactly one mandatory trust-root source: inline `expected_hash` or canonical `expected_hash_file`. The file's exact content is one checked `hash:<64 uppercase hex>#<CRC16>` NetworkId literal followed by one LF; CRLF and unterminated aliases are rejected. Production templates use `/run/iroha/genesis.expected_hash`; the same Kagami-generated file feeds client `network_id_file`, so the two security domains cannot drift. The referenced manifest carries parameter families such as `transaction.max_signatures`, `transaction.max_instructions`, `transaction.ivm_bytecode_size`, `transaction.max_tx_bytes`, `transaction.max_decompressed_bytes`, and `transaction.max_time_to_live_ms`; update the manifest when tightening admission limits. `max_time_to_live_ms` defaults to one day and is the on-chain ceiling for every signature-bound transaction TTL. Configuration normalization resolves the expected hash independently of the artifact before it reads a genesis body from the local file or Kura. A configured artifact must match the hash. Genesis must have exactly one block signature at index zero, signed by `public_key`; its first transaction authority and exact header hash must match the same resolved anchor. A fresh node also needs the complete local signed artifact; a restarting node may use the matching body already stored in Kura. Empty storage with only a hash fails because Iroha has no peer genesis retrieval protocol. Signed snapshot exports do not replace the original genesis and certified replay history; retired `snapshot.bootstrap` configuration is rejected. See `specs/startup_trust_roots.md` for the startup ordering and operator checklist.
- `[network]`: P2P addresses, gossip periods/sizes, DNS refresh, bounded queue capacities, mandatory TLS 1.3 transport, dormant optional QUIC, and automatic SCION preference when both peers advertise support. The lockfile resolves patched `quinn 0.11.12` / `quinn-proto 0.11.18`; `quic_enabled=true` still fails before binding pending complete transport requalification. `quic_datagrams_enabled` remains conservatively false, and mandatory TLS-over-TCP carries all P2P topics. `network.address` is the authenticated TLS listener; there is no plaintext listener or retry knob. Deferred outbound sends are bounded by age, per-peer count/stream-wire bytes, and the true-total `network.deferred_send_max_bytes_total` cap (128 MiB by default). The total owner keeps an additive authenticated-consensus safety reserve; ordinary traffic cannot consume it.
- Consensus ingress guardrails: `network.consensus_ingress_rate_per_sec`/`consensus_ingress_burst` cap per-peer consensus/control frames (`null` disables), `network.consensus_ingress_bytes_per_sec`/`network.consensus_ingress_bytes_burst` cap payload volume, `network.consensus_ingress_critical_rate_per_sec`/`consensus_ingress_critical_burst` and `network.consensus_ingress_critical_bytes_per_sec`/`network.consensus_ingress_critical_bytes_burst` apply dedicated caps to liveness-critical messages (fallback to the standard caps when both critical caps are unset; penalty cooldowns apply in that fallback), and `network.consensus_ingress_penalty_threshold` + `network.consensus_ingress_penalty_window_ms` + `network.consensus_ingress_penalty_cooldown_ms` temporarily suppress peers that exceed the standard caps. Revision-4 `Proposal` (including its `PayloadManifest`), `Vote`, `QuorumCertificate`, timeout, `PayloadChunk`, body/certificate requests, `CommitCertificateResponse`, and `GlobalBeaconPartialSignature` traffic use the critical ingress policy; `CertifiedBodyResponse` and BlockSync traffic use the bulk policy. These node-local resource caps do not alter the signed full-committee quorum or mandatory RS16 protocol.
- `[ivm]`: Runtime presentation settings. Guest stack geometry is fixed by `IvmStackPolicy::V1`; node configuration cannot override it.
- `[pipeline]`: Transaction pipeline parallelism and caches. `pipeline.workers` (0 = auto) sets the worker pool used for the stateless pre-pass, access derivation, and overlay construction; `pipeline.stateless_cache_cap` bounds the stateless validation cache (0 disables it) so identical transactions can skip repeat pre-pass checks until TTL/clock-drift windows expire.
- `[tiered_state]`: Hot/cold WSV tiering knobs (`enabled`, `hot_retained_keys`, `hot_retained_bytes`, `hot_retained_grace_snapshots`, `cold_store_root`, `da_store_root`, `max_snapshots`, `max_cold_bytes`). If `cold_store_root` is unset, snapshots are stored under `da_store_root`; changing either root resets tiering metadata.
- `[concurrency]`: Native thread-pool sizing and stack budgets for Tokio runtime/blocking threads, scheduler/prover workers, and Sumeragi helpers. `tokio_stack_bytes` defaults to 8 MiB and is validated within 8–64 MiB. These operational settings do not alter guest-visible IVM memory geometry. The V1 guest policy always uses a 64 KiB floor, 4 MiB ceiling, four stack bytes per gas unit, and 16-byte alignment.
- `network.peer_gossip_period_ms` (default: `1000`ms) also governs the topology refresh cadence. The `IROHA_P2P_TOPOLOGY_UPDATE_MS` env override is now ignored; adjust the config field instead. Peer-address gossip backs off when idle up to `network.peer_gossip_max_period_ms`, and block-sync sampling backs off up to `network.block_gossip_max_period_ms`. Gossip periods (`block_gossip_period_ms`, `block_gossip_max_period_ms`, `transaction_gossip_period_ms`, `peer_gossip_period_ms`, `peer_gossip_max_period_ms`), `idle_timeout_ms`, `preauth_timeout_ms`, and `reply_writer_flush_timeout_ms` are clamped to a minimum of 100ms to avoid tight loops. `preauth_timeout_ms` defaults to 30 seconds and is one non-renewable deadline from accepted transport through signed peer authentication; established peers continue under `idle_timeout_ms`. `preauth_max_connections_per_ip` defaults to 8 and bounds concurrent accepted-but-unauthenticated transports from one canonical source IP; operators may raise it when legitimate peers share a NAT. `reply_writer_flush_timeout_ms` defaults to 30 seconds and is the base deadline for one exact reply's peer-writer occurrence; only an observed timeout increases that item's next deadline, while a successful full flush resets it.
- SCION transport selection is capability-driven and automatic: peers advertise `scion_supported` in handshake/trust metadata and peer gossip, and outbound dialing prefers SCION-capable paths only when both sides advertise support. After QUIC is dependency-qualified, peers without SCION capability may use it when requested; while the dependency gate is active they use mandatory TLS. Raw TCP is never a peer transport. No `network.scion_*` keys exist; retired keys are rejected as unknown fields.
- `network.trust_gossip` (default: `true`) advertises support for TrustGossip frames. Setting it to `false` negotiates the capability off at handshake time, dropping TrustGossip messages while leaving peer-address gossip intact. Drops are tagged via `p2p_trust_gossip_skipped_total{direction,reason}` so operators can spot opt-outs or peers that refused the capability.
- Trust scoring knobs under `[network]` (`trust_decay_half_life_ms`, `trust_penalty_bad_gossip`, `trust_penalty_unknown_peer`, `trust_min_score`) apply in permissioned overlays: trust frames that reference peers outside the active topology incur the unknown-peer penalty, increment `p2p_trust_penalties_total{reason="unknown_peer"}`, and senders below `trust_min_score` are ignored until decay recovers. Public/NPoS overlays skip the unknown-peer penalty so trust gossip remains open.
- Transaction gossip tuning: `network.transaction_gossip_drop_unknown_dataspace` drops batches for dataspaces missing from the lane catalog; `network.transaction_gossip_restricted_target_cap` caps restricted fanout to the authorized native lane validators (default: all); `network.transaction_gossip_public_target_cap` caps public-lane fanout (default 16, set `null` for broadcast); `network.transaction_gossip_public_target_reshuffle_ms` and `network.transaction_gossip_restricted_target_reshuffle_ms` control how often target selection reshuffles per plane (defaults to `transaction_gossip_period_ms`, clamped to ≥100ms); `network.transaction_gossip_resend_ticks` sets how many gossip periods elapse before re-sending the same transactions. Restricted payloads use only the committee authenticated by committed native lane state; missing authority or unavailable recipients defer delivery without using the public overlay. Telemetry and `/status.tx_gossip` expose caps, selected recipients, outcomes, and drop reasons.
- `network.soranet_handshake.pow`: Mandatory challenge configuration for SoraNet admission; there is no `required` switch. Fields: `difficulty`, `max_future_skew_secs`, `min_ticket_ttl_secs`, `ticket_ttl_secs`, `revocation_store_capacity`, `revocation_store_ttl_secs`, and `revocation_store_path`. The replay store controls how many consumed raw or signed ticket fingerprints are retained on disk and how long they remain authoritative for replay detection; its TTL must be at least `max_future_skew_secs` so every accepted ticket stays consumed through expiry.
- `network.soranet_handshake.pow.puzzle`: mandatory Argon2 puzzle settings. The first-release resource corridor is `memory_kib = 4096..=131072`, `time_cost = 1..=8`, `lanes = 1..=16`, and static `difficulty = 1..=32` (default `6`). The standalone relay uses the same single configured difficulty and rejects an `adaptive` key as unknown. Runtime updates outside those bounds are rejected atomically. Handshake security policy is node-local operator configuration and is never accepted from or propagated through P2P messages.
- `network.soranet_handshake.kem_suite`: Optional textual override (`"mlkem512"`, `"mlkem768"`, or `"mlkem1024"`; `kyber*` aliases are also accepted) for the ML-KEM profile used during the SoraNet handshake. When set it supersedes `kem_id`. The bundled default capability vectors are synchronized with this selection and with `descriptor_commit`; custom vectors must explicitly advertise the selected KEM on both roles and make the relay `snnet.transcript_commit` value match the configured descriptor commitment.
- `[sumeragi]`: Node-local Sumeragi settings only: the participation `role` (`validator` or `observer`), consensus signing-key policy under `keys`, and the credential-free global beacon share signer binding `global_beacon_partial_signer_provider_{handle,revision,policy_digest_hex}`. Consensus mode, the exact `3f + 1` committee, leader selection, quorum and block size and transaction limits are chain parameters from signed genesis and committed state, never node settings. Retired tables such as `advanced`, `block`, `collectors`, `da`, `debug`, `gating`, `limits`, `npos`, `persistence`, `queues`, `recovery` and `storage`, along with fault switches such as `conflicting_ready_mask` and `duplicate_inits`, are rejected rather than ignored. The optional local-parameter overrides of `specs/sumeragi.md` §12.4 are `view_timeout_base_ms`, `view_timeout_max_ms`, `start_level_cap`, `start_level_decay_after`, `rebroadcast_interval_ms`, `status_keepalive_ms`, `build_timeout_ms`, `fetch_retry_ms`, `sync_batch`, `sync_retry_ms`, `sync_max_bytes` and `max_observers` (unset values take the §9.3 default for the committee size; zero intervals and a zero `sync_batch` are rejected). `records_dir` holds the safety records (default `<kura.store_dir>-sumeragi-records`, a sibling of the Kura store, which it must not be inside), `installation_log` the key installation log (default `<kura.store_dir>-sumeragi-installation.log`; must be outside `records_dir`) and `retired_keys` the consensus keys retired by a rotation (never the node's own key, no duplicates).
- `[torii]`: Public API server settings such as listen address, request size caps, and query store parameters.
- `[musubi_publication]`: Non-secret custody root, private TLS bind/mount and request concurrency, durable journal operation/authorization/response/snapshot limits, exact-CAR seed retention, and seed-receipt clock skew/lifetime. Paid-pin settings select `pin_storage_class` (`hot`, `warm`, or `cold`; default `hot`), `pin_retention_horizon_secs` (default 30 days; strictly longer than the 24-hour SoraFS ingest deadline and at most 365 days), and `pin_transaction_authority` (default `ingress_broker`, or one canonical domainless I105 account). The chosen account must have a qualified runtime signer and enough funds for the current public SoraFS pin fee and transaction fees before submission. These settings carry public identity only; credentials, TLS keys, provider authentication, and finalized deployment identities remain in runtime custody. Configuration alone does not activate the private publisher.
- `[torii.faucet]`: Optional server-signed account creation/funding mutation. If the
  table is present, `pow_difficulty_bits` must be non-zero; the default is `18`,
  while an operator may explicitly choose a lower positive value for a bounded
  development deployment. The public puzzle uses
  first-release `scrypt-leading-zero-bits-v1` algorithm and
  `iroha:accounts:faucet:pow:v1` challenge domain, carries the canonical exact
  `NetworkId` and I105 chain discriminant, and hashes the raw 32-byte
  `NetworkId` immediately after that domain. Claims always require the
  advertised anchor and nonce; pre-release labels are rejected, and the route
  is a protocol-authenticated mutation, not a public read.
- `torii.api_tokens` supplies the credential allow-list for Torii API-token
  authentication. `torii.require_api_token` applies that allow-list to the
  listener except for the anonymous local SoraFS CID/site gateway routes. It is
  an exact pair: requiring tokens needs `1..=256` distinct entries, while a
  disabled token gate forbids a non-empty allow-list. Each entry is `32..=256`
  visible ASCII bytes without whitespace. Empty, padded, control-bearing,
  duplicate, and oversized values fail configuration parsing rather than being
  normalized, and configuration debug output never renders the token text. It is
  not route-level authority: ISO 20022, webhook management, and SoraFS
  stream-token issuance require fresh exact-network operator signatures before
  request-body decoding. Public SoraFS reads accept only canonical content in
  the node's authoritative local store and do not accept client storage tokens.
- Torii App API pagination limits are exact non-zero values.
  `app_api_max_list_limit` and `app_api_max_fetch_size` must each be at least
  `app_api_default_list_limit`; Torii rejects reversed or zero bounds instead of
  silently raising them. Optional Torii rate and burst values must be non-zero
  when present.
- Proof request limits (`proof_max_body_bytes`, `proof_body_read_timeout_ms`,
  `proof_max_list_limit`, `proof_request_timeout_ms`,
  `proof_cache_max_age_secs`, and `proof_retry_after_secs`) are non-zero and are
  applied exactly. Explicit zero proof rate, burst, or egress budgets are invalid.
- `[torii.connect]` requires non-zero global sessions, session TTL, frame and
  buffer sizes, ping intervals/miss tolerance, and dedupe TTL/capacity. The ping
  interval must be at least the browser minimum. Zero remains meaningful only
  for the documented per-IP session cap, per-IP handshake rate, and P2P hop TTL.
- `torii.api_rate_limit_bypass_cidrs`: Effective client CIDRs that bypass
  Torii's API request-rate limit only. Broad subnets are permitted because this
  field grants no authentication, internal-read, or target-account routing
  privilege; body-size, admission, and credential checks still apply.
- `torii.internal_api_trusted_cidrs`: Exact effective transport source hosts
  trusted for unprojected `/v1/internal/*` reads and unsigned target-account
  routing. Entries must be IPv4 `/32` or IPv6 `/128`; broader networks are
  rejected during configuration parsing. The default trusts only
  `127.0.0.1/32` and `::1/128`. When a request arrives through a configured
  trusted proxy, this policy is evaluated against Torii's validated effective
  client address.
- `torii.transport.trusted_proxy_cidrs`: Explicit proxy transport hosts
  (`/32` for IPv4 or `/128` for IPv6) whose
  `X-Forwarded-For` chain Torii may use for client-IP rate limits and CIDR
  policy. Network-wide and wildcard trust ranges are rejected during
  configuration parsing. A trusted proxy must overwrite the header or append
  its observed source address. Torii walks the chain from the transport side,
  ignores any attacker-selected prefix before the first untrusted address,
  rejects malformed or longer-than-32-hop chains, and never accepts the
  internal `x-iroha-remote-addr` header from the network.
- `[torii.transport.http]`: HTTP/1 socket and request-head limits enforced
  before request middleware. `max_connections` defaults to `1024`, while
  `max_connections_per_ip` defaults to `64` and cannot exceed the global
  limit. `header_read_timeout_ms` and `write_timeout_ms` default to `10000`
  and `30000` and must be non-zero. `max_headers` defaults to `100` and is
  capped at `1024`; `max_header_bytes` defaults to `65536` and must remain in
  the inclusive `8192..=1048576` range.
- `[torii.transport.https]`: optional native HTTPS listener on the same fully
  authenticated Torii router. Omitting `address` disables HTTPS; configuring it
  requires a leaf-first `certificate_chain` of one to four DER file paths and a
  `private_key` DER path. Paths resolve relative to their configuration file and
  use the native private-file reader (each file at most 16 KiB). Invalid or
  mismatched keys fail startup before listeners or workers start. The absolute
  `handshake_timeout_ms` defaults to `10000` and must be in `1..=120000`.
  HTTP and HTTPS share the configured global/per-IP socket pool, HTTP head/body
  bounds, route authorization and shutdown owner. TLS advertises HTTP/1.1 only
  and disables early data. This transport does not establish provider admission,
  current service eligibility or cold-package readiness.
- `torii.preauth_allow_cidrs`: Explicit source hosts that bypass the
  pre-authentication resource gate. It accepts only IPv4 `/32` and IPv6 `/128`
  entries, plus `127.0.0.0/8` as the local-host loopback range; broad remote
  subnets cannot disable pre-authentication admission.
- `torii.preauth_ban_capacity`: Maximum active temporary pre-authentication
  bans retained in memory (default: `4096`). The store purges expired entries
  first and evicts the earliest-expiring live entry at capacity, keeping
  attacker-controlled source addresses from growing the ban store without
  bound.
- `[torii.transaction_ingress]`: Physical transaction-submission resource corridor.
  `max_concurrent_compute_jobs` (default: `4`) bounds blocking transaction
  admission work: batch-envelope and transaction decode, canonicalization,
  signature verification and routing across single,
  entrypoint, and batch submission routes. Torii fails fast when all slots are
  occupied, and each owned slot remains in the physical worker until it exits
  even if the HTTP request times out or disconnects.
  `max_batch_transactions` (default: `512`) is the exact top-level transaction
  count accepted by `/v1/pipeline/transactions/batch`. Torii authenticates and
  enforces encoded and declared-decoded byte limits before compute admission,
  then uses Norito's authoritative sequence decoder to reject count overflow
  before decoding any signed transaction payload. Canonical retries precede fresh
  queue pressure. Batches use per-entry certified admission after full preflight:
  202 confirms all inputs; 207 returns every input's signed hash, status and reject
  code. Partial acceptance is durable, so clients reconcile each uncertain entry
  and never automatically resend the whole batch.
  `verified_source_max_concurrent_compiles` (default: `1`, V1 maximum: `4`)
  bounds complete Kotodama compiler working sets for verified-source jobs. Its
  fail-fast permit is acquired before Torii polls or decodes the signed request
  body and moves into the blocking compiler worker, so disconnecting a client
  cannot admit replacement compilation while the detached worker still runs.
  `verified_source_body_read_timeout_ms` (default: `10000`) is the absolute
  deadline for completing that already-admitted bounded body read.
- `torii.receipt_public_key` / `torii.receipt_private_key` (optional): Dedicated key pair used to sign transaction and DA submission receipts. If omitted, `irohad` deterministically derives a domain-separated Secp256k1 receipt key from the node identity, so receipts remain verifiable across ordinary restarts without reusing the node key. Set both values when receipt identity must remain independent of node-key rotation; BLS keys are rejected here—use Ed25519 or Secp256k1. Torii refuses to start when its durable DA receipt log cannot be opened or verified, rather than starting a permanently unusable DA endpoint.
- `[torii.operator_signatures]`: Mandatory exact-request authentication for every route cataloged as `OperatorSignature`. `enabled` must remain true for those routes to be usable; disabling it fails them closed rather than falling back to sessions or bearer tokens. `allow_node_key` and `allowed_public_keys` define the signer allowlist, while `max_clock_skew_secs`, `nonce_ttl_secs`, and `replay_cache_capacity` bound freshness and replay state. `body_read_timeout_ms` (default: `10000`) is the absolute limit for collecting each bounded raw body before verification; expiry releases admission and returns `408 Request Timeout`. Each signature binds the runtime `NetworkId`, method, path, sorted query, raw body hash, timestamp, and nonce.
- `[torii.operator_auth]`: Optional WebAuthn/mTLS second factor for operator endpoints. When `enabled`, mTLS (if configured) and a valid `x-iroha-operator-session` are required in addition to the exact operator request signature; they never substitute for it. `require_mtls` expects `X-Forwarded-Client-Cert` from an edge peer in `mtls_trusted_proxy_cidrs`. Every trusted edge must remove any inbound copy of that header and insert it only after authenticating the client certificate; Torii deliberately treats the configured edge as the certificate-authentication boundary. `tokens` is the dedicated `x-iroha-operator-token` allowlist for first-credential bootstrap: entries are unique 32..=256-byte visible-ASCII values without whitespace, registration accepts them only while no WebAuthn credential exists, and they never authorize ordinary operator routes. An enabled empty credential store must have at least one such token or startup fails; after the first credential is persisted the token list may be removed. Listener `x-api-token` values are not reused for operator authentication. Once the first credential is persisted, only an authenticated session may enroll rollover credentials. `rate_per_minute`/`burst` apply to auth attempts, `ephemeral_state_capacity` independently bounds live challenges, sessions, and lockout identities, `credential_capacity` bounds persisted authenticators, and `lockout_failures`, `lockout_window_secs`, and `lockout_duration_secs` control temporary lockouts. Capacity admission first removes expired entries and never evicts live authentication state. Full challenge and session stores fail closed; a full lockout store preserves tracked locks but declines new failure identities so attacker-chosen identities cannot reject an otherwise valid unseen caller. Missing-mTLS denials do not consume lockout entries. Persisted credentials are validated strictly at startup; corrupt, duplicate, disallowed-algorithm, or non-canonical key records prevent Torii from starting instead of silently disabling recovery. Operational failures remain visible in telemetry but do not count as invalid credentials. `webauthn` is required when `enabled = true` and configures `rp_id`, `rp_name`, `origins`, `user_id`, `user_name`, `user_display_name`, `challenge_ttl_secs`, `session_ttl_secs`, `require_user_verification`, and `allowed_algorithms`. Enabled startup fails when any of the seven dependencies is missing, substituted, stale, unavailable, or test-marked, including when the constructed transparency producer cannot reconcile its signed authoritative head; disabled configuration rejects every dormant runtime binding. Torii owns a supervised transparency worker only while the viewer and its publisher are enabled. At the configured compaction cadence, every publication tick fresh-reconciles the signed external head, reads a fresh service audit checkpoint, and walks at most 16 signed-projection pages of 256 receipts each. Consecutive failures skip 1, 3, then at most 7 cadence ticks and emit payload-free logs; shutdown stops and joins the worker. - `[crypto]`: Cryptography defaults surfaced via `iroha_config`.
  - `sm_intrinsics` (default: `auto`): SM intrinsic dispatch policy.     - `sm2_distid_default` (default: `1234567812345678`): Fallback SM2 distinguishing identifier applied when signers omit their own `distid`. The node seeds `Sm2PublicKey::default_distid()` with this value during startup, so updates take effect before any transactions execute.

  **SM rollout checklist.** The `iroha_config` layering (`defaults` → `user` → `actual`) allows staged rollouts:
  1. **Build validation.** Compile binaries with `--features sm` (and `sm-ffi-openssl` only if the preview backend is required). Without the feature flag the node rejects `sm2` in `allowed_signing`.
  2. **Configuration propagation.**
     - Update `crypto.allowed_signing` to include `sm2` (keep the list lexicographically sorted) and set `crypto.default_hash = "sm3-256"`.
     - Override `crypto.sm2_distid_default` with the distinguishing identifier mandated by your policy (e.g., the ISO/TC 68 value for your organisation).
  3. **Genesis alignment.** Regenerate genesis manifests via `kagami genesis generate --consensus-mode <mode>` (use `--allowed-signing sm2 --default-hash sm3-256` if you need overrides) so the `parameters` blocks and injected metadata mirror the config snapshot. The final ordered BLS topology and original proofs of possession define validator generation zero. Validate the signed NPoS scheduling parameters and committee geometry before signing; keep each matching private validator key on its host.
  4. **Telemetry & admission smoke tests.** Before turning on traffic, run `cargo test -p iroha_crypto --features sm` and the SM integration matrix scripts, then verify `/status` exposes `crypto.sm_helpers_available = true` and that Torii rejects SM2 signatures when `sm2` is absent from `allowed_signing`.
  5. **Rollback plan.** Document how to revert to Ed25519-only mode (remove `sm2` from `allowed_signing`, restore `default_hash = "blake2b-256"`) and confirm hosts drop in-flight SM transactions deterministically.

Notes
- Acceleration is automatic by default. Backends run golden self-tests on first use and disable themselves at runtime if a mismatch is detected; the VM falls back to scalar/SIMD and remains bit-identical across hardware.
- Prefer editing `peer.template.toml`-style files and extending them in deployment. Runtime behavior is configured via `iroha_config`; node startup with `--config` ignores ambient environment-variable aliases so a checked or integrity-bound TOML artifact cannot be rewritten by the launcher environment. The no-config deterministic-development path and tests may still exercise explicit environment inputs.
