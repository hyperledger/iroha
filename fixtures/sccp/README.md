# SCCP fixtures

Shared SCCP v1 vectors (`specs/sccp.md` §11). They are generated by Rust, by
the independent Python reference (`scripts/sccp_reference/`), by both (the
revision 5 reference vectors, which the two generators write byte for byte) or
by the contracts themselves, and consumed by the contract suites (EDR, Acton),
the node and the SDKs.

Conventions of the Rust-generated files: byte strings are `0x`-prefixed
lowercase hex; integers that can reach `2^53` or more (`u128` amounts,
`ton_amount_bound`) are decimal strings and every other integer is a JSON
number; rejected inputs name the `iroha_sccp::v1` error variant that rejects
them (for example `TrailingBytes`, `BadControl` or `BadOffset`).

## Rust-generated v1 vectors

`crates/iroha_sccp/tests/v1_vectors.rs` regenerates four current files and
fails when a committed file differs. It cross-checks Merkle/history paths,
native BLS certificates, destination proof bindings and calldata decoder
verdicts. The mixed tree uses native 199-byte control leaves; its explicit
certificate/effect identities are synthetic DATA, not Parliament authorization.
`control_v1.json` is generated separately by the reference writers below.

| File | Content |
|---|---|
| `payload_v1.json` | The four profiles (tag, domain, identity word, `network_bytes`, route id, account codec); payloads for all 6 directions with `deadline_ms`, payload hashes, lane bytes and message ids (§3.2, §3.3); `taira_units` conversions and rejected amounts (§0); rejected payload encodings covering every §3.1/§3.2 rule, including the retired TRON domain 5 (both directions) and codec 5 (as a sender and as a recipient) |
| `commitment_tree_v1.json` | 512 mixed transfer/control leaves (`leaf_rule`), worked transfer, control and node preimages, roots and every path for counts 1..=17 and 512 including promoted nodes, and confusion negatives (internal node as leaf, transfer leaf at a control position, flipped pause, count and path mismatches) |
| `history_v1.json` | 40 history leaves (`leaf_rule`), and for sizes 1..=40 the root, the right-bagged peaks and every path (§3.5) |
| `evm_calldata_v1.json` | Genuine native BLS committee/certificate scenarios, direct and checkpoint finalization, checkpoint batches, full native control payloads and history references, `voidExpired`, `voidExpiredFromCheckpoint`, `voidFrozen` and `transferToTaira`; every current selector/topic, committee/initial-committee/pause-state view, transfer and void logs, and exact calldata bytes. The conformance table preserves separate Rust strict-decoder and Solidity ABI verdicts for trailing bytes, offsets, padding, integer/boolean encodings and range mutations; contract replay checks those recorded verdicts rather than assuming they always agree |

Common inputs: the Taira `NetworkId` is `0x11…11` (the §3.4 example value),
the base time is `1 800 000 000 000` ms and outbound deadlines are one day
later, and the synthetic payload-address key `i` has secret
`keccak256("SCCP/FIXTURE/KEY/V1" ‖ u8 i)`. Codec-3 (`taira_account`) fields
are opaque byte strings; contracts check only their length (§3.1). The EVM
destination word is `word(0x22…22)`.

Regenerate after a reviewed layout change, then review the diff:

```text
scripts/cargo_fast.sh --stable-local-metadata --jobs 2 -- \
  test --locked -p iroha_sccp --test v1_vectors regenerate_v1_vectors -- --ignored --exact
scripts/cargo_fast.sh --stable-local-metadata --jobs 2 -- \
  test --locked -p iroha_sccp --test v1_vectors v1_vectors_match_committed_fixtures -- --exact
python3 scripts/ton_sccp_builder.py vectors
python3 scripts/ton_sccp_builder.py vectors --check
```

`native_transfer_event_v1.json` holds the inbound transfer and void vectors
of every source: the `SccpTransferToTaira` and `SccpVoided` logs (Ethereum,
BSC) and the `sccp_transfer_to_taira` external-out body `BoC` with its minter
(TON), each with the normalized event Taira derives.
`crates/iroha_sccp/tests/ethereum_light_client.rs` regenerates it with
`--ignored regenerate_native_transfer_event_v1` and runs the Ethereum and TON
vectors through their light clients.

`governance_v1.json` and `ton_bodies_v1.json` of the §11 table are added with
the governance payload and TON message-body code that generate them.

## Reference vectors (revision 5)

`finality_v1.json`, `committee_transitions_v1.json` and `control_v1.json`
follow `specs/sccp.md` revision 5. Two independent generators write them, and
their outputs are byte-identical, so either one regenerates the three files:

- **The Python reference**, `scripts/sccp_reference/`: a dependency-free
  re-derivation of the contract-visible relation, with its own Keccak-256,
  BLS12-381 with the optimal ate pairing, RFC 9380 hash-to-G2 under `DST_SIG`,
  the min-pk proof-of-possession signatures, payloads and message ids, transfer
  and 199-byte control leaves, the promote-odd tree and the history
  accumulator, the 221-byte finality header `X` (X1–X7 and the inactive form),
  `R`, the 116-byte `QC_FIXED`, the 165-byte Commit preimage `P`, committee
  roots, checkpoint ids, anchors and forgery evidence ids, and an executable
  model of the §5.1 destination state machine.
- **The Rust reference**, the `crates/iroha_sccp` integration tests
  `v1_reference_finality`, `v1_reference_transitions` and
  `v1_reference_control` (shared code in `tests/reference_support/`), built on
  `iroha_sccp::v1::{finality, committee}` and `iroha_crypto::bls::consensus`.
  Each has a drift test `reference_<file-stem>_matches_committed_fixture` and
  an ignored `regenerate` test.

`bls_consensus_v1.json` stays in this directory and is written by the Python
reference alone. It has no byte-for-byte Rust generator: the
`iroha_crypto::bls::consensus` tests
(`crates/iroha_crypto/src/signature/bls/consensus/tests/python_reference.rs`)
read it from this directory only and reproduce it row by row. Its `generator`
and `rust_only_vectors` entries say the same, and the vectors that need the
w3f transcript are rows of `bls_consensus_rust_v1.json` (below), not of this
file.

Conventions: byte strings are `0x`-prefixed lowercase hex, field elements are
`0x` hex integers, `u128` amounts and nonces passed to `voidFrozen` are
decimal strings, and every other integer is a JSON number. Outcomes are `ok`
or a §5.2.2 error name; a latch or a lost `Live` inside `submitCheckpoints` is
`ok` with `stopped`. `committee_transitions_v1.json` repeats under
`error_choices` the error names and the check order that §5.1.2, §5.1.3 and
§5.1.8 fix (not `Live`: `Equivocated` when latched, `CommitteeNotAccepted`
when expired; `QC_FIXED`, signature and `signerYs` lengths: `BadCertificate`;
`X` length: `BadHeader`; committee length and signer-key encodings, including
an EVM signer `x ≥ p` and the coordinates `(0, 0)`: `BadCommittee`; the
identity signature on both flavours, signature encodings and pairing:
`BadSignature`; an identity aggregate key: `BadCommittee` on EVM and
`BadSignature` on TON, whose only verdict is the result of
`BLS_FASTAGGREGATEVERIFY`; an aggregate key outside G1: `BadSignature`; a
stored checkpoint that is neither of the current generation nor the handoff
that installed it: `CommitteeNotAccepted`; the `voidFrozen` range:
`BadAmount` on EVM, `BadRange` on TON, checked before `Frozen`; a TON
finalize or void checks the payload and its recipient before it obtains `X`,
EVM after). The
cheap path is mandatory (§5.1.3 step 8): no deployment carries a switch for
it, the model always takes it after the checks of steps 1–6, and
`SccpCertificate` appears only on full verifications. No call of the model
aborts for arithmetic: the two time sums and `opCount` saturate at `2^64 − 1`
(§5.1.1, §5.1.2), and a sender's source nonces end at `2^64 − 2` (§5.1.7; the
models carry that rule as a function, since they do not model burns). JSON
numbers stay below `2^53`, so those extremes are pinned in
`pytests/scripts/test_sccp_reference.py` and in the Rust unit tests, not in
rows. The Taira `NetworkId` is `0x11…11`, `I` is `0x77…77` and the EVM
destination word is `word(0x22…22)`.

Flavour and profile: an EVM row runs on `ethereum-mainnet`, and a TON row on
`ton-mainnet` with Taira's leaves on the TON lane, 36-byte recipients and the
placeholder minter account id `0x35…35` as destination word. Both models
refuse any other pair. A TON row names the TON message of each step
(`sccp_checkpoint`, `sccp_finalize_checkpoint`, …; `ton_call_names` maps
them). An `SccpCertificate` event names the pooled certificate whose
`QC_FIXED`, header and signature the destination published, among the
certificates of its own step. `init_bounds` lists the deployment bound on the
pinned `untilMs`.

Time: `now_ms` is the destination clock, `block.timestamp × 1000` on EVM and
`now() × 1000` on TON (§0). Every `now_ms` of a scenario step is therefore a
multiple of 1000 and never decreases within a scenario (equal values are
calls in one block), and the Python recorder fails generation otherwise.
`X.timestamp_ms`, `untilMs`, payload deadlines and fast-pause expiries are
Taira-side milliseconds and may be sub-second. A time boundary is probed at
the boundary value and at the nearest clock value on its other side, one
second away. Three scenarios probe a sub-second boundary at the whole seconds
on both sides of it: `rotation_sub_second_deadline` (an `untilMs`),
`transfer_deadline_boundaries` (a `deadline_ms` ending in 999 ms) and
`fast_pause_sub_second_expiry` in `control_v1.json` (a `fastPauseUntilMs`
ending in 001 ms).

Regenerate after a reviewed change with either generator, then review the
diff (a new row needs both generators and one regeneration):

```text
python3 scripts/sccp_reference/generate.py --write
cargo test -p iroha_sccp --test v1_reference_finality \
    --test v1_reference_transitions --test v1_reference_control \
    -- --ignored regenerate
```

The first command needs Python 3.10 or later and also rewrites
`bls_consensus_v1.json`; the second can run through `scripts/cargo_fast.sh`
like the command of the section above. Drift is checked on both sides:
`python3 scripts/sccp_reference/generate.py --check` (the default mode), the
three Rust tests without `--ignored`, and
`pytest pytests/scripts/test_sccp_reference.py`, which runs the Python drift
check together with the cross-checks (RFC 9380, the ethereum/bls12-381-tests
inputs, the captured mainnet aggregate, values from `blst`, the Rust
`payload_v1.json`, `commitment_tree_v1.json` and `history_v1.json`, the
destination clock rule, and the two Rust-only files below).

### Rust-only vectors

Two files carry the vectors that need the w3f transcript of `iroha_crypto`,
which the dependency-free Python reference does not implement. Rust generates
and drift-checks them. `pytests/scripts/test_sccp_reference.py` checks with
the Python reference every row of `finality_rust_v1.json`, and of
`bls_consensus_rust_v1.json` every row it can decide without the w3f
transcript: the standard sign, verify and aggregate vectors, the allowlist
rows and rejections, and the key and consensus-API negatives. The proofs of
possession (`keys[].w3f_pop`) and the verdict of the generic-API negative stay
Rust-only. The pytest fails on a missing file and on a row shape it does not
know:

| File | Content |
|---|---|
| `finality_rust_v1.json` | Schema `iroha.sccp.finality.rust.v1`: the §11.3 negative certificate whose aggregate is a w3f-transcript signature over the consensus digest, with its expected rejection (`BadSignature` at the pairing check). Generated and drift-checked by `crates/iroha_sccp/tests/v1_reference_finality.rs`; its rows have the shape of the `negative_certificates` rows of `finality_v1.json` |
| `bls_consensus_rust_v1.json` | Schema `iroha.bls_consensus.rust.v1`: the standard sign, verify and aggregate vectors, the consensus allowlist rows with their signatures and the allowlist rejections, the pinned w3f proofs of possession, and negatives (a w3f-transcript signature over a consensus preimage and over a consensus digest, a `DST_SIG` signature presented to the generic API, a proof of possession used as a signature, malformed keys and signatures, keys that aggregate to the identity). Generated and drift-checked by `iroha_crypto` (`consensus_vectors_match_committed_fixture`, ignored `regenerate_bls_consensus_rust_v1`) |

## Contract-generated vectors

`ton_stateinit_v1.json` is emitted by the Tolk contracts
(`contracts/ton/sccp/scripts/stateinit-golden.tolk`) and cross-checked by
`scripts/generate_ton_sccp_stateinit_golden.py` (§5.3.1). It pins the
canonical minter initial data, the minter, bucket (canonical, not activated)
and wallet addresses and the code cell hashes and depths. The Rust
`iroha_sccp::v1::ton_cell` unit tests recompute every vector from the recorded
code references and pin the `n4` native committee deployment values.
